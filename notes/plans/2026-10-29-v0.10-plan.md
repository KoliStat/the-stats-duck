# 0.10 cycle plan

Date: 2026-10-29, reordered 2026-10-30. Status: the plan for the 0.10 cycle.
The GitHub milestone `0.10.0` tracks the issues; this note records the order,
the reasons and the cut lines. Branch `v0.10`, created from `main` at
`98aa4e3` (the 0.9.0 merge commit).

The first version of this note led with correctness fixes. On 2026-10-30 the
order was changed to: VISUALIZE first, then the bugs, then the release
mechanics, then a bounded set of kernel improvements. The sections below are
in that order.

## Where 0.9 left things

0.9.0 was released on 2026-10-28: tag `v0.9.0` on `98aa4e3`, the GitHub
release `v0.9.0-here-s-your-nine-pence`, and the registry bump
duckdb/community-extensions#3440 (merged 2026-10-29). The cycle shipped
`glm_fit`, `emmeans`, `ptukey`/`qtukey`, `lin_hyp`, rank-deficient fits,
function descriptions, and the DuckDB 2.0 port.

The registry built the 2.0.0 line only. DuckDB 1.5.6 users still get 0.8.0
from `INSTALL stats_duck FROM community` until duckdb/community-extensions#3449
(the `variegata` and `andium` keys) is merged and a 1.5.6 build is run. The
1.4.x line has been disabled registry-wide since 2026-06-18.

Three things were deferred on purpose and are part of this cycle:

- The PR #80 code review left three findings for 0.10: the unregistered
  t-test table forms (#55), the copies of `SetD` and `EvalConst` (#82), and
  `emmeans`' own copy of the `p_adjust` method table (#83).
- The 2.0 port left the deprecation warnings (#79) and the grammar hooks for
  `VISUALIZE` (#46). The port found that the hooks are an upgrade, not a
  requirement: the parser-extension fallback still works on 2.0.
- Eleven issues were filed while building 0.9, two of them crashes or wrong
  numbers (#69, #81).

The kernel roadmap ends with 0.9 for the core: survival and mixed models go
to the bio repo (#28), which is a parallel track and not part of this plan.

## Scope, in priority order

### 1. VISUALIZE: close the gap with ggsql, and use the grammar hooks on 2.0

Upstream ggsql is at 0.5.2 (released 2026-09-11; no release since), and
ggsql-duckdb 0.5.2 has been in the community registry since 2026-10-09,
excluded from every wasm platform. Ours is the one ggsql-style `VISUALIZE`
that runs in the browser, which is what bedevere-wise uses through
duckdb-wasm 1.4.3. Two things do not change in this cycle: the output model
(`spec` plus `layer_sqls`, the client runs the SQL) and support for the
1.4.x and 1.5.x lines.

The gap survey in #58 (2026-10-01, against 0.5.2) is still current. Its
tiers are the work list. Each item becomes its own issue under #58 when it
is picked up, with its own test.

**1a. Syntax convergence in the hand parser.** The hand parser in
`src/ggsql_grammar.cpp` serves all three DuckDB lines, so every syntax
change lands there first and reaches the wasm consumer. Tier 1 of #58:

- Accept `VISUALISE`.
- Channel aliases: `colour` to color, `label` to text, `ymin`/`ymax` to
  y/y2, `xend`/`yend` to x2/y2.
- The `path` and `segment` marks.
- Mark aliases: `range` to errorbar, `ribbon` to errorband, `tile` to
  heatmap, `smooth` to the loess line.
- The `linewidth` and `linetype` channels.
- `SCALE ... REVERSE`, `SCALE ... VIA log|sqrt|symlog`, `SCALE BINNED`.

Plus the two syntax differences that stop upstream examples from running at
all: clauses in any order, and the trailing form `SELECT ... VISUALISE x, y
DRAW point` with implicit `x`, `y` mapping (upstream's hello world). In the
hand parser the SELECT part becomes the layer source, the way a leading
`WITH` is carried today.

The progress measure is a new test file, `test/sql/ggsql_compat_upstream.test`,
made of statements copied from the syntax and gallery pages of ggsql.org.
Each statement must parse and produce a spec. The number of passing
statements is the number to report.

**1b. Tier 2 of #58**, in this order: per-layer `FILTER`, `PARTITION BY`
and `ORDER BY`; `SETTING position => 'stack' | 'dodge' | 'jitter'`;
`LABEL key => 'text' | null`; bar auto-count, histogram `bins` and
`binwidth`, boxplot `coef`. If time remains: `SETTING` literal aesthetics as
mark properties, and facet `free`, `ncol`/`nrow` and 1-D wrap.

**1c. The grammar hooks on DuckDB 2.0.** This is the parser item left in
#46. The mechanism, as shipped in 2.0.0 and as duckpgq and psql use it:

- A `GrammarExtension` whose `GetChanges()` returns `GrammarChange`s:
  `AddRule` for the VISUALIZE rules, `PrependChoice("Statement", ...)` for
  the standalone statement, a choice on the select rules for the trailing
  form, and `SetTransformProcess` for the transform.
- The transform builds the existing `VisualizeStatement` and wraps it in an
  `ExtensionStatement` with the existing parser extension. `GgsqlPlan`, the
  spec generator and `layer_sqls` do not change. This is what duckpgq does
  for `CREATE PROPERTY GRAPH`.
- Aesthetic expressions go through DuckDB's own `Expression` rule and are
  written back with `ToString()` for the layer SQL. That also removes the
  reconstructed spacing of the 2.0 token adapter.
- Keywords that are not DuckDB keywords (`DRAW`, `FACET`, ...) match by
  text, as in duckpgq, so no reserved words are added and `draw` stays
  usable as a column name.
- `active_grammar_extensions` is a connection-local setting. psql activates
  itself on every connection at load, through `ExtensionCallback::
  OnConnectionOpened` for new connections and a `QueryEnd` state for the
  ones already open. We do the same, so `VISUALIZE` keeps working without a
  `SET`; `RESET active_grammar_extensions` is the opt-out.
- The parser-extension fallback stays. It is the only path on 1.4.x and
  1.5.x, and on 2.0 it serves a connection that has reset the grammar.

Test rule: the `ggsql_*` suite passes on 2.0 both with the grammar active
and after `RESET active_grammar_extensions`. How the second run is wired (a
test-time switch or a second CI step) is decided in the spike.

Order: after 1a, so the grammar is written once against the converged
syntax. Gate: a one-day spike that runs the hello world through the grammar
before the full port. The API was called a preview in August 2026, but
duckpgq and psql ship on it in 2.0.0, so the risk is low. The spike also
answers whether 1b's clauses are cheaper to add in the grammar than in the
hand parser; they are still added to both.

**1d. Small VISUALIZE issues.** #39 (VARCHAR-backed channels are typed
`quantitative` and render empty; the most visible bug), #40 (Vega-Lite v6
`$schema`, two lines), #48 (violin facet header title), #49
(`EXTENSION_VERSION` in chart footers).

### 2. Correctness

- **#81, `pnorm` lower tail and `1 - CDF` p-values.** `NormalCDF` cancels
  below about z = -8 and every upper-tail p-value is computed as `1 - CDF`,
  so anything below 1e-16 comes back as exactly 0. Fix: `NormalCDF` through
  `erfc`, an explicit upper-tail function for the normal, t, F and chi-square
  references through the complementary incomplete beta and gamma, and every
  `1 - CDF` site in the tests, the fitters and `lin_hyp`/`emmeans` rewritten
  to call it. Tests pin small p-values against scipy down to the subnormal
  range. This is one change across `distributions.hpp` and the p-value
  sites, so it goes first in this block and alone.
- **#69, `OVER ()` segfault.** Find out what DuckDB expects from a
  window-capable aggregate that the STRUCT-returning aggregates do not
  provide. Either provide it or reject at bind time with a message that
  names `GROUP BY`. One SQL test per aggregate, and a check of every
  STRUCT-returning aggregate, not only the three reported.
- **#70, #53, #54.** Small, independent, each with its own test.

### 3. Release mechanics

- **#9**: a CI job that builds the three wasm flavors against DuckDB 1.4.3
  (the version `@duckdb/duckdb-wasm` bundles) and commits them to `docs/`.
  In 0.9 this was a local emsdk build, the one release step a machine
  cannot do yet.
- **Tag trigger**: the distribution pipeline has no `tags:` trigger. The
  merge push deploys both the latest and the versioned set, and the
  versioned set is filed under the commit hash because the tag does not
  exist yet. Decide whether to add the trigger (a second deploy per release,
  named by the tag) or to leave it and record the hash as the version
  label.
- **Registry keys**: the 0.10.0 bump sets `variegata` and `andium` to the
  merge commit, next to `ref`, so the 1.5.6 line is built from the start
  (see the checklist below).
- **Function descriptions**: the community page shows the first line of
  each description only. Give `glm_fit` and `emmeans` a one-sentence first
  line with the details after a newline, and remove the em and en dashes
  from the four descriptions that carry them.
- **#79**: a `ToUnified` shim in `duckdb_compat.hpp` for the counted form,
  and the two `DataChunk` calls handled per site.
- **README**: lines 43 and 451 promise features that have shipped
  (Spearman and Kendall, regression, multiple-testing corrections) and name
  CR2/CR3 as a planned follow-up. Rewrite or remove.

### 4. Kernel, a bounded set

- **#44, `CholFactor`**: unblocked since #33 landed, and what the bio repo's
  `lmm_fit` needs from the core.
- **#72, the Tukey multiplier cache**: 28.5 s against 0.16 s at 1000 rows;
  measure the one-entry cache first.
- **#76, tolerance bands**: re-measure every band across fixtures and
  platforms, then tighten with the margin written beside it.
- **#66**: the relative tolerance for the negative-variance guard in
  `lin_hyp`, matching `emmeans`.

### Cleanups, when the files are open

#55, #82, #83 and #77, in that order (#82 and #77 touch the same file).
They are not a block of their own: each is done when its file is open for
another change, or at the end if time remains.

  First candidate for 0.11.
- The rest of #58: the Tier 2 items marked "if time remains" above, and all
  of Tier 3 (`PROJECT TO polar`, axis flip, `spatial`, `PLACE`, `RENAMING`,
  `polygon`).
- The rest of #46: the C-ABI port and the signed self-hosted repository. A
  written verdict as a comment on #46 if time remains; no code either way.
- #51, panel data: reframe it in general longitudinal terms (any

- #73, #75, #71 (kernel) and #27 (exact nonparametric tails) stay optional.
- #28, the bio repo, runs in parallel outside this repository.

## Order and sizing

0.9 ran twelve weeks with three large features. The target here is eight
weeks:

1. Weeks 1 and 2: 1a (Tier 1, the two syntax forms, the compatibility test
   file) and 1d.
2. Weeks 3 and 4: 1b, then the 1c spike and the grammar port.
3. Weeks 5 and 6: #81 first and alone, then #69, #70, #53, #54; then #44
   and #72.
4. Weeks 7 and 8: #9, the tag-trigger decision, the registry keys, the
   description first lines, #79, the README, #76, #66, the cleanups whose
   files are open, and the release.

If the cycle slips, the cut line is in this order: the "if time remains"
items of 1b, then #76 and #66, then the cleanups.

The codename is `here` (decided 2026-10-29): the release is
`0.10.0-here` in the CHANGELOG heading and in CITATION.cff, and the tag
stays `v0.10.0`.

## Conventions carried over

- Feature branches `feat/<issue>-<name>` into `v0.10`; the distribution
  pipeline does not run on pull requests into `v0.*`, so a full matrix
  before the release PR is a `workflow_dispatch` on the branch.
- Stage files explicitly; the `duckdb` submodule is expected-dirty (the
  applied fmt patch recorded in `patches/`).
- Run the SQL suite with the absolute test path; a relative `test/sql/*`
  runs DuckDB's own tests.
- Every tolerance band carries a measured reason (`docs/fitter_conventions.md`).
- Plain English in code comments, commit messages and documents.

## Release checklist for 0.10.0, as practiced for 0.9.0

1. Refresh `docs/v1.4.3/{wasm_eh,wasm_mvp,wasm_threads}` against DuckDB
   1.4.3 (local emsdk until #9 lands) and run `scripts/wasm-verify`.
2. Date commit: CHANGELOG heading and CITATION `date-released`.
3. PR `v0.10` -> `main`. Expect GitHub's macOS runner capacity to cancel a
   cell now and then; `gh run rerun <id> --failed` once the run completes.
4. Merge with a merge commit; the push to `main` deploys.
5. Tag `v0.10.0` on the merge commit (annotated, codename in the message).
6. GitHub release titled with the codename, notes condensed from the
   CHANGELOG section.
7. Registry bump from the KoliStat fork, branch `bump-v0.10.0`: `version`,
   `ref`, `variegata` and `andium` all set to the merge commit, keep
   `opt_in_platforms`. The registry builds the latest stable line on the
   PR; the 1.5.6 line needs the `variegata` key and a maintainer's
   dispatch (or the automation in duckdb/community-extensions#3436).
8. The community page regenerates every two hours from whichever binary the
   newest CLI can install. A page generated within minutes of the deploy
   can still show the previous binary; wait for the next run.
