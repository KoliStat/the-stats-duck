# 0.10 cycle plan

Date: 2026-10-29. Status: the plan for the 0.10 cycle. The GitHub milestone
`0.10.0` tracks the issues; this note records the order, the reasons and the
cut lines. Branch `v0.10`, created from `main` at `98aa4e3` (the 0.9.0
merge commit).

## Where 0.9 left things

0.9.0 was released on 2026-10-28: tag `v0.9.0` on `98aa4e3`, the GitHub
release `v0.9.0-here-s-your-nine-pence`, and the registry bump
duckdb/community-extensions#3440 (open, CI green). The cycle shipped
`glm_fit`, `emmeans`, `ptukey`/`qtukey`, `lin_hyp`, rank-deficient fits,
function descriptions, and the DuckDB 2.0 port.

Three things were deferred on purpose and are the seed of this cycle:

- The PR #80 code review left three findings for 0.10: the unregistered
  t-test table forms (#55), the copies of `SetD` and `EvalConst` (#82), and
  `emmeans`' own copy of the `p_adjust` method table (#83).
- The 2.0 port left the deprecation warnings (#79) and the rest of #46 (the
  PEG grammar hooks for `VISUALIZE`, the signed self-hosted repository).
- Eleven issues were filed while building 0.9, two of them crashes or wrong
  numbers (#69, #81).

The kernel roadmap ends with 0.9 for the core: survival and mixed models go
to the bio repo (#28), which is a parallel track and not part of this plan.

## Scope, in priority order

### 1. Correctness

These are must-haves. A release that still computes a p-value of 0 for a
strong effect, or crashes the process on `OVER ()`, is not one to ship.

- **#81, `pnorm` lower tail and `1 - CDF` p-values.** `NormalCDF` cancels
  below about z = -8 and every upper-tail p-value is computed as `1 - CDF`,
  so anything below 1e-16 comes back as exactly 0. Fix: `NormalCDF` through
  `erfc`, an explicit upper-tail function for the normal, t, F and chi-square
  references through the complementary incomplete beta and gamma, and every
  `1 - CDF` site in the tests, the fitters and `lin_hyp`/`emmeans` rewritten
  to call it. Tests pin small p-values against scipy down to the subnormal
  range. This is one change across `distributions.hpp` and the p-value
  sites, so it goes first and alone.
- **#69, `OVER ()` segfault.** Find out what DuckDB expects from a
  window-capable aggregate that the STRUCT-returning aggregates do not
  provide. Either provide it or reject at bind time with a message that
  names `GROUP BY`. One SQL test per aggregate, and a check of every
  STRUCT-returning aggregate, not only the three reported.
- **#70, #39, #53, #54.** Small, independent, each with its own test.

### 2. DuckDB 2.0 follow-through

- **#79**: a `ToUnified` shim in `duckdb_compat.hpp` for the counted form,
  and the two `DataChunk` calls handled per site.
- **#55, #82, #83, #77**: delete the dead t-test table forms, share the two
  helpers, share the method table, and split `glm_fit_function.cpp`, in that
  order, since #82 and #77 touch the same file.
- **#46 spike**: a written verdict on the C-ABI port and the PEG grammar
  hooks, as a comment on #46. Does the stable API cover aggregates that
  write LIST and STRUCT vectors, table functions, the COPY writers and the
  parser hook, and what happens to wasm? No code commitment in 0.10 either
  way.

### 3. Kernel and performance

- **#44, `CholFactor`**: unblocked since #33 landed, and what the bio repo's
  `lmm_fit` needs from the core.
- **#72, the Tukey multiplier cache**: 28.5 s against 0.16 s at 1000 rows;
  measure the one-entry cache first.
- **#76, tolerance bands**: re-measure every band across fixtures and
  platforms, then tighten with the margin written beside it.
- **#66**: the relative tolerance for the negative-variance guard in
  `lin_hyp`, matching `emmeans`.
- **#65, Type I and II sums of squares**: this needs a term model before
  any code. Decide in the first week: either a design note in this
  directory, or move the issue to 0.11. It is the only candidate for a new
  modelling feature in this cycle.
- If time remains: #73, #75, #71.

### 4. Release mechanics

- **#9**: a CI job that builds the three wasm flavors against DuckDB 1.4.3
  (the version `@duckdb/duckdb-wasm` bundles) and commits them to `docs/`.
  In 0.9 this was a local emsdk build, the one release step a machine
  cannot do yet.
- **Tag trigger**: the distribution pipeline has no `tags:` trigger. The
  merge push deploys both the latest and the versioned set, and the
  versioned set is filed under the commit hash because the tag does not
  exist yet. Decide whether to add the trigger (a second deploy per release,
  named by the tag) or to leave it and record the hash as the version
  label.
- **README**: lines 43 and 451 promise features that have shipped
  (Spearman and Kendall, regression, multiple-testing corrections) and name
  CR2/CR3 as a planned follow-up. Rewrite or remove.

## Not in 0.10

- VISUALIZE: #58 (the ggsql gap tiers), #40 (Vega-Lite v6), #48, #49. Pick
  one of the cheap #58 items only if the four blocks above are done.
- #51, panel data: reframe it in general longitudinal terms (any
  unit-by-time grid), or route it to the bio repo. As written it leans
  clinical, which is not the core's positioning.
- #27 (exact nonparametric tails) stays optional.
- #28, the bio repo, runs in parallel outside this repository.

## Order and sizing

0.9 ran twelve weeks with three large features. The blocks above are mostly
bounded fixes, so the target is four to six weeks:

1. Weeks 1 and 2: #81 first and alone, then #69, then the #65 decision and
   #44.
2. Weeks 3 and 4: the 2.0 block (#79, #55, #82, #83, #77), #72, #76, #66,
   the small correctness fixes.
3. Weeks 5 and 6: #9, the tag-trigger decision, the README fix, the #46
   spike, and the release.

The codename is `here` (decided 2026-10-29): the release is
`0.10.0-here` in the CHANGELOG heading and in CITATION.cff, and the tag
stays `v0.10.0`.

## Conventions carried over

- Feature branches `feat/<issue>-<name>` into `v0.10`; the distribution
  pipeline does not run on pull requests into `v0.*`, so a full matrix
  before the release PR is a `workflow_dispatch` on the branch.
- Stage files explicitly; the `duckdb` submodule is expected-dirty (the
  applied fmt patch recorded in `patches/`).
- Run the SQL suite with the absolute test path; a relative `test/sql/*`
  runs DuckDB's own tests.
- Every tolerance band carries a measured reason (`docs/fitter_conventions.md`).
- Plain English in code comments, commit messages and documents.

## Release checklist for 0.10.0, as practiced for 0.9.0

1. Refresh `docs/v1.4.3/{wasm_eh,wasm_mvp,wasm_threads}` against DuckDB
   1.4.3 (local emsdk until #9 lands) and run `scripts/wasm-verify`.
2. Date commit: CHANGELOG heading and CITATION `date-released`.
3. PR `v0.10` -> `main`. Expect GitHub's macOS runner capacity to cancel a
   cell now and then; `gh run rerun <id> --failed` once the run completes.
4. Merge with a merge commit; the push to `main` deploys.
5. Tag `v0.10.0` on the merge commit (annotated, codename in the message).
6. GitHub release titled with the codename, notes condensed from the
   CHANGELOG section.
7. Registry bump from the KoliStat fork, branch `bump-v0.10.0`: `version`,
   `ref` = the merge commit, keep `opt_in_platforms`.
